# Gugu Flash Project Delivery Department Plan

项目负责人视角结论：Gugu Flash 当前已经不是“只有想法”的阶段，而是一个产品逻辑、Mock API、Web 原型、状态规则和自动化测试都初步成形的 MVP 雏形。下一阶段的核心不是继续堆概念，而是把 Mock 原型升级成可登录、可审核、可运营、可真机同步、可小范围上线的产品。

## 1. 当前判断

### 已经具备

- Web/H5 原型：Feed、播放器、创作、Remix、IP 池、专区申请、我的作品、商店、设备页、运营台。
- 共享规则层：`GuguH5Pack`、IP/分身、商店状态、硬件包状态、设备权益、下架保留使用权。
- Mock API facade：未来真实后端路由和当前前端调用之间已有可替换接口。
- 测试底座：内容校验、核心单元测试、API 契约测试、Playwright 关键路径测试。
- 产品边界：H5 发布、商店上架、硬件包制作、设备下载是独立生命周期。

### 主要缺口

- 没有真实账号、权限、用户资料、设备归属和订单后端。
- 没有真实素材上传、资产审核、版权材料、内容安全扫描。
- 没有真实审核后台工作流和运营权限。
- 没有真实支付、退款、结算、发票、风控。
- 没有 Native App 和真机 BLE/同步链路。
- Web UI 仍偏原型，尚未达到面向真实用户的完成度。
- HardwarePack 制作仍是规则模拟，没有真正的硬件适配工具链和真机验证。

## 2. 产品完成定义

MVP 上线不是“所有长期愿景都完成”，而是满足以下交付标准：

- 用户可以注册/登录，浏览、播放、创作、发布和 Remix H5 作品。
- 二创必须选择 IP 池，原创/二创、素材来源、权利承诺可追溯。
- H5 发布、商店上架、硬件包制作、设备下载各自有独立状态和审核记录。
- 运营可以审核作品、处理上架、处理投诉、下架内容、查看操作日志。
- 用户可以绑定至少一种真实设备，购买/领取 HardwarePack，并同步到设备。
- 下架、退款、投诉、同步失败、设备切换等高风险状态不会破坏用户权益。
- 关键规则有自动化测试，发布前有真机验收清单。

暂不纳入 MVP：

- 真实多人共创。
- 个性化推荐大模型。
- 用户现金分成和提现。
- 完整小程序能力。
- 大规模开放 UGC 商业化。

## 3. 部门分工

### 产品部

负责人：产品负责人 / PM。

任务：

- 锁定 MVP 范围，维护需求优先级和版本节奏。
- 输出 PRD：账号、创作器、审核、商店、设备、运营后台、版权治理。
- 定义核心指标：有效播放数、合格发布作品数、上架通过率、设备同步成功率、投诉处理时效。
- 组织每周评审：需求变更、风险、延期、上线准入。

交付物：

- MVP PRD。
- 状态机和异常流程清单。
- 版本验收表。
- 每周项目风险表。

### 设计部

负责人：UX/UI Lead。

任务：

- 把当前 Web 原型改造成生产级移动端体验。
- 梳理用户路径：新用户浏览、创作、发布、申请上架、绑定设备、商店下载。
- 降低概念负担：IP、分身、专区、上架、设备包要用用户能懂的语言。
- 输出 Native App、Web 分享页、运营后台三套设计规范。

交付物：

- 移动端核心流程 Figma。
- Web/H5 分享页设计。
- 运营后台信息架构。
- 文案规范和空状态规范。

### 前端部

负责人：Frontend Lead。

任务：

- 将 `apps/web` 从单文件原型拆成可维护的页面、组件、状态和 API adapter。
- 接入真实 API，同时保留 Mock 模式用于演示和测试。
- 完成 Web/H5 分享页、创作器、作品详情、个人主页、IP 页、商店页。
- 建立前端错误处理：登录失效、审核失败、同步失败、支付失败、权限不足。

交付物：

- 生产级 Web/H5 客户端。
- Mock/Real API adapter 切换。
- 前端组件和页面测试。
- 埋点事件上报。

### 后端部

负责人：Backend Lead。

任务：

- 建立 Gugu Flash 自有后端，不依赖废弃的 guguclub。
- 实现 User、Session、Work、WorkVersion、Asset、IPEntry、Persona、IPZone、ReviewTask、StoreListing、HardwarePack、Order、Device、DeviceEntitlement、DeviceInstall。
- 实现统一 `/flash/**` API，按当前 `packages/api-client` 契约迁移。
- 建立权限、操作日志、审计日志、异步任务、对象存储和消息队列。

交付物：

- 后端服务和数据库 schema。
- API 文档和 SDK。
- 管理后台权限模型。
- 数据迁移和备份方案。

### AI 与创作工具组

负责人：AI Product Engineer / Creator Tool Lead。

任务：

- 把当前 prompt-to-draft Mock 替换为真实 AI adapter。
- AI 输出必须是结构化 JSON，并通过 `GuguH5Pack` 校验后才能保存。
- 做结构化编辑器：场景、台词、选项、结局、封面、标签、素材来源。
- 支持续写、改语气、补分支、标题/标签建议。

交付物：

- AI 生成服务 adapter。
- 创作器编辑器。
- AI 输出校验和失败重试策略。
- 素材来源和版权声明表单。

### 审核与安全治理部

负责人：Trust & Safety Lead。

任务：

- 建立三层审核：H5 发布审核、商店上架审核、硬件适配审核。
- 建立举报、投诉、申诉、拉黑、评论隐藏、限流、下架机制。
- 建立 IP 风险分级、素材来源审核、权利投诉处理。
- 未成年人和高风险社交边界保持保守：MVP 不开放陌生人私信、CP 绑定和付费关系玩法。

交付物：

- 审核标准和 SOP。
- 权利投诉和申诉流程。
- 内容安全标签体系。
- 运营处理时效 SLA。

### 硬件与 Native 部

负责人：Mobile/Hardware Lead。

任务：

- Native App 作为主同步客户端，优先完成设备绑定、设备状态、下载、BLE 同步、失败回滚。
- 定义真实设备能力读取：型号、固件、电量、空间、屏幕、协议版本。
- 实现 HardwarePack 下载、checksum 校验、安装、回读当前运行内容。
- 建立真机测试矩阵和固件兼容策略。

交付物：

- iOS/Android MVP App。
- BLE/同步 SDK。
- 设备绑定和同步链路。
- 真机兼容报告。

### 硬件内容工作室

负责人：Hardware Studio Lead。

任务：

- 建立从 H5 WorkVersion 到 HardwarePack 的官方适配流程。
- 输出兼容性报告，记录降级动作，生成独立 HardwarePack 版本。
- 建立预览、打包、资源预算、checksum、发布流程。
- 不允许普通用户直接生成设备代码。

交付物：

- Hardware Studio MVP。
- H5 到 HardwarePack 适配规范。
- 打包和预览工具。
- 官方内容制作队列。

### 测试与质量部

负责人：QA Lead。

任务：

- 把当前 `npm test` 和 `npm run test:e2e` 纳入 CI。
- 扩展状态机、权限、支付、退款、下架、设备同步失败测试。
- 建立 release 前验收：Web、Native、运营台、真机、支付、审核、数据回滚。
- 对核心路径做回归清单，不追求早期 100% 覆盖率。

交付物：

- CI 流水线。
- 自动化测试集。
- 真机验收报告。
- Release checklist。

### 运营与内容部

负责人：Content/Ops Lead。

任务：

- 准备官方 IP、官方分身、新手内容、免费 HardwarePack。
- 组织首批创作者内测，收集创作难点和优质作品。
- 制定 IP 入池、专区申请、精选推荐、下架通知的运营规则。
- 上线前准备客服话术、审核模板、活动节奏。

交付物：

- 首批官方内容包。
- 创作者内测名单。
- 运营后台使用手册。
- 用户公告和客服 FAQ。

### 商业化与法务财务

负责人：Biz/Legal/Finance Lead。

任务：

- MVP 只做官方免费/低价 HardwarePack 和用户作品荣誉精选，不急着开放现金分成。
- 设计订单、退款、权益撤销、收益冻结、权利投诉联动。
- 明确二创商业化边界、素材授权材料、用户承诺条款。
- 支付和退款先接真实闭环，结算和创作者分成后置。

交付物：

- 用户协议、创作者协议、商店上架条款。
- 支付/退款规则。
- 权利投诉处理政策。
- 商业化二期方案。

## 4. 里程碑安排

### M0：范围冻结与工程拆分，1 周

目标：

- 锁定 MVP 范围和不做事项。
- 把原型拆分成真实工程任务。
- 明确 API、数据库、客户端、硬件、运营台的负责人。

验收：

- PRD v1、技术方案 v1、排期 v1、风险表 v1 完成。

### M1：真实后端与生产级 Web Alpha，4 周

目标：

- 后端核心实体和 `/flash/**` API 可用。
- Web 从 Mock 切到真实 API 的主链路跑通。
- 用户能登录、发布 H5、申请上架，运营能审核。

验收：

- Feed、创作、发布、审核、上架申请在真实数据库中闭环。
- 单元测试、契约测试、Web smoke 测试通过。

### M2：运营审核、版权治理、素材上传，4 周

目标：

- 素材上传、素材来源、版权承诺、投诉、申诉、评论治理落地。
- 运营后台从演示变成可工作的工具。

验收：

- 审核动作有操作人、理由、证据、时间。
- 投诉可以冻结推荐、商店和收益占位。
- 上架通过才能进入硬件制作队列。

### M3：Native 与真机同步 Beta，6 周

目标：

- Native App 完成登录、设备绑定、设备页、商店页、下载和同步。
- BLE/同步链路有失败诊断、重试和回滚。
- HardwarePack 有真实打包、checksum 和兼容报告。

验收：

- 至少一种真实设备完整跑通购买/领取、下载、同步、回读。
- 低电量、空间不足、固件过低、下架包、无权益都能正确拦截。

### M4：小范围内测，3 周

目标：

- 20-50 名创作者、50-200 名种子用户、若干真实设备。
- 观察创作、审核、上架、同步、投诉和客服负载。

验收：

- 设备同步成功率达到上线阈值。
- 审核 SLA 可控。
- 崩溃率、投诉率、退款率、同步失败率在可接受范围。

### M5：公开 MVP 上线，2 周

目标：

- 上线官方内容、Web 分享、Native 主客户端、运营后台、有限商店。
- 保持 UGC 商业化克制，先以官方内容和精选荣誉为主。

验收：

- Release checklist 全绿。
- 线上监控、客服、运营值班、回滚预案准备完成。

## 5. 关键依赖

- 后端 API 是前端、Native、运营台和小程序的共同依赖，必须优先。
- 审核和版权治理是商店与硬件适配的准入依赖，不能等上线后补。
- Native 和硬件同步依赖 HardwarePack 打包规范、设备能力读取和 checksum。
- 支付/退款依赖 Order、DeviceEntitlement、DeviceInstall 三个对象稳定。
- 运营内容依赖官方分身、官方 IP、新手包和审核 SOP。

## 6. 风险与管控

### 版权与 IP 风险

管控：

- 二创必须选 IP 池。
- 商店上架必须提交素材来源和权利承诺。
- 权利投诉成立前可以先冻结推荐、商店和收益占位。

### 设备同步失败风险

管控：

- 同步前做电量、空间、固件、权益、包状态、checksum 检查。
- 写入失败保留原运行内容。
- 每次失败生成诊断码。

### 产品范围膨胀风险

管控：

- MVP 暂停真实共创、现金分成、复杂推荐、小程序完整能力。
- 所有新增需求进入 PM 评审，不直接打断当前里程碑。

### UGC 治理风险

管控：

- MVP 不开放陌生人私信、CP 绑定和付费关系玩法。
- 评论必须有举报、拉黑、隐藏、删除、限流和审核记录。
- 未成年人和未知年龄按保守策略处理。

## 7. 每周项目例会机制

周一：

- 产品确认本周目标、阻塞项和跨部门依赖。

周三：

- 技术联调会，重点看 API、前端、Native、硬件同步、运营台。

周五：

- Demo 和风险评审，所有部门展示可运行结果，不只汇报文档。

上线前每日：

- 缺陷清单、风险清单、回归结果、真机结果、客服和运营准备同步。

## 8. 立即行动清单

1. 产品部冻结 MVP v1 范围，把真实共创、现金分成、复杂推荐移出首发。
2. 后端部按 `packages/api-client` 契约启动真实 `/flash/**` API。
3. 前端部拆分 `apps/web/src/app.js`，准备接真实 API。
4. 设计部重做移动端主流程，重点降低 IP、分身、上架、设备包概念负担。
5. 审核治理部先写 H5 发布、商店上架、硬件适配三层审核 SOP。
6. Native/硬件部定义首个支持设备型号、BLE 协议和真机验收清单。
7. 硬件内容工作室准备首批官方免费 HardwarePack。
8. QA 把现有单元测试和 E2E 接入 CI，并扩展支付、退款、下架、同步失败回归。
9. 运营部准备首批种子内容、创作者名单、客服 FAQ。
10. 法务财务确认商店条款、版权投诉、退款和用户作品精选规则。
