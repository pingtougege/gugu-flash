# Gugu Flash Product Issues Plan

这份文档只收敛“还没想清楚/还没做完整”的问题，不重复描述已经实现的原型功能。后续可以按条逐个展开成独立方案文档、PRD 或技术设计。

## 使用方式

- `P0`: 不解决会阻塞上线或导致高风险。
- `P1`: 不阻塞原型验证，但会影响真实产品闭环。
- `P2`: 增强体验、增长或运营效率。
- 每个问题都保留“需要决策”，方便逐项讨论。

## 01. 内容审核链路不完整

优先级：`P0`

现状：

- 当前作品发布基本是直接进入 `public_h5`。
- 商店上架只有 `rights_review -> listed` 的简化流。
- 官方台可以批准上架、标记硬件候选，但没有完整审核队列。

风险：

- 不适合真实 UGC 上线。
- 无法处理违规内容、版权争议、投诉、复审和下架。
- 运营记录不可追踪，后续很难解释某个作品为何被推荐或下架。

建议方向：

- 拆成三层审核：H5 发布审核、商店上架审核、硬件适配审核。
- 每层都有提交材料、审核状态、审核人、理由、驳回、复审、下架。
- 先做最小可用队列，不急着做复杂权限系统。

需要决策：

- H5 发布是否默认先审后发，还是低风险内容先发后审？
- 二创内容是否允许进入公开推荐？
- 哪些状态必须人工审核，哪些可以自动通过？

建议产出：

- `docs/review-workflow-plan.md`

## 02. IP 与版权治理不足

优先级：`P0`

现状：

- 创作时区分 `original` 和 `fanwork`。
- 已确认二创必须从平台 IP 池选择 IP。
- 商店上架要求用户勾选 IP/素材授权风险承诺。

风险：

- 用户承诺不能完全转移平台责任。
- 热门 IP、明星真人、游戏/动漫素材、同人二创都可能带来投诉。
- 一旦进入商店或硬件适配，平台参与度更高，风险更大。

建议方向：

- 建立 IP 风险分级：原创、平台授权、用户声明二创、高风险真人/IP、来源不明素材。
- 商店上架需要材料字段：授权说明、素材来源、是否使用第三方角色/图片/音频。
- 建立投诉和下架机制：权利人通知、用户申诉、收益冻结、证据留存。

需要决策：

- 已确认 IP 入池只做轻审核，重点看重复、明显违规和治理风险。
- 已确认商店上架必须要求素材来源说明。
- 已确认权利投诉初步成立时，可以先下架/限流/冻结，再进入用户申诉。
- 已确认 disputed IP 暂停商店和硬件链路。

建议产出：

- `docs/ip-rights-policy-plan.md`

## 03. 商店内容与硬件适配边界不清

优先级：`P0`

现状：

- 商店现在展示 `storeStatus = listed` 的作品。
- 硬件状态使用 `hardwareStatus` 表示 H5 only、候选、可下载。
- 原型里商店购买/下载/同步已经可以跑通，但仍是模拟逻辑。
- 已确认用户申请上架后，后台会专门制作硬件内容包，制作和审核通过后用户才能下载。

风险：

- “商店上架”不等于“硬件可运行”。
- H5 内容可能适合浏览，但不适合设备屏幕、性能、内存和交互限制。
- 用户可能误解购买的是 H5 作品还是硬件内容包。

建议方向：

- 拆出两个商业对象：`StoreListing` 和 `HardwarePack`。
- 商店展示和下载的是后台制作完成的 `HardwarePack`，不是用户原始 H5。
- 硬件适配通过 Gugu Flash 官方 Hardware Studio 生成，不允许用户直接下发代码。

需要决策：

- 已确认商店下载对象是后台制作并审核通过的硬件内容包。
- 已确认 HardwarePack 下架后，已安装设备内内容可以继续使用。
- 已确认购买权益按设备区分，每台设备需要单独购买/领取，不按账号通用。

建议产出：

- `docs/store-hardware-boundary-plan.md`

## 04. 共创还没有真正成立

优先级：`P2 / 暂缓`

当前决策：

- 暂不做共创，不进入当前 MVP。
- 当前阶段保留个人创作和 Remix。
- 好友页里的共创邀请可以作为概念占位，但不实现真实流程。

现状：

- 当前有 Remix，但没有多人实时/异步共创。
- 好友页有共创邀请的展示，但没有真实接受、编辑、归属和发布流程。

风险：

- 产品还停留在“个人创作 + 二创”，没有形成社交协作壁垒。
- 多人作品的权利、收益、署名、撤回都会成为后续问题。

建议方向：

- 先做异步共创，不做实时协同编辑。
- 共创单位是一个 `collabDraft`，可以邀请好友补台词、补选项、补结局。
- 发布前确认贡献者、署名顺序、是否允许 Remix、是否允许上架。

需要决策：

- 共创作品收益如何分配？
- 共创成员是否都要签署商店上架承诺？
- 一个成员退出后，作品能否继续发布？

建议产出：

- `docs/co-creation-plan.md`

## 05. IP 池与角色分身体系还只是模板

优先级：`P1`

现状：

- 当前有 4 个官方分身：雨天咕咕、汽水咕咕、零点列车长、工位小闪。
- 分身会显示在 Feed、播放器、草稿、商店和好友动态中。
- 当前“专区”仍是题材标签，并不是按 IP/世界观划分。

风险：

- 分身目前只是创作字段，不是可沉淀的身份资产。
- 用户无法自建分身，也无法关注某个分身。
- 分身和 IP/版权之间的边界还没有定清楚。
- 二创如果允许自由手填 IP，会导致版权治理、专区聚合、角色归属和上架审核都失控。

建议方向：

- 建立平台 IP 池，二创必须从 IP 池选择 IP。
- 专区按 IP/世界观/原创企划划分，不按题材划分。
- 分身必须属于某个 IP，是该 IP 内的角色；专区开通后再在专区内组织和展示。
- 情绪陪伴、摸鱼上班、同频搭子、像素冒险改为题材频道或模板标签。
- 先做官方 IP 和官方分身库，再开放用户创建原创 IP 和角色分身。

需要决策：

- 已确认用户可以创建原创 IP，轻审核后进入 IP 池。
- 已确认用户可以在 IP 下创建角色分身。
- 已确认真人明星/公众人物分身禁止。
- 已确认动漫/游戏等角色分身必须归属对应 IP。
- 已确认官方分身可以商业化。
- 已确认分身是 IP 内角色资产，不是账号孤立资产。
- 已确认用户原创 IP 可设置角色开放权限：open / approval / private。

建议产出：

- `docs/ip-pool-persona-zone-plan.md`

## 06. 专区还不是社区

优先级：`P1`

现状：

- 已确认专区应按 IP/世界观/原创企划划分。
- 当前原型里的情绪陪伴区、摸鱼上班区、同频搭子区、像素冒险区应降级为题材频道。
- 当前还没有真正的 IP 专区页。

风险：

- 没有专区页时，用户很难形成稳定圈层。
- 推荐流会变成孤立作品消费，缺少社区归属。
- 如果专区仍按题材划分，角色分身、二创、Remix 和版权治理会缺少归属容器。

建议方向：

- 做 IP 专区首页：IP 介绍、治理状态、角色分身列表、热门作品、创作/Remix 入口、专区规则。
- 每个 IP 专区有推荐分身、题材标签、运营活动。
- 二创必须从 IP 池选择 IP，不能手填。
- IP 入池不自动生成专区，专区需要满足作品和热度门槛后由用户申请开通。

已确认规则：

- 有 IP 不等于有专区。
- IP 审核通过只代表进入 IP 池，不自动生成专区。
- 专区是 IP 社区空间，不是题材专区。
- 专区需要满足作品数、创作者数、热度和风险门槛后才能申请。
- 专区由用户申请开通。
- 申请者需要邀请若干用户共同成立专区。
- 专区申请通过后，申请者自动成为 `zone_admin`。
- `zone_admin` 是运营管理员，不等于 IP 权利人。
- 专区可设置角色开放权限：`open / approval / private`。
- 专区作品流展示 `Work`。
- 专区商店/硬件展示 `HardwarePack`。
- `disputed / restricted / blocked` IP 会联动影响专区展示、商店和硬件。
- 题材频道只做跨 IP 聚合，不拥有作品。
- 支持 IP 合并和旧专区跳转。

建议产出：

- `docs/ip-pool-persona-zone-plan.md`
- `docs/ip-zone-community-plan.md`

## 07. 创作器能力太浅

优先级：`P1`

现状：

- 当前一句话生成固定结构草稿。
- 用户只能改标题和标签，不能编辑场景、分支、台词、角色、封面、音效。

风险：

- 用户很快会遇到表达天花板。
- 作品之间容易同质化。
- 高质量内容难以产生，影响商店和硬件精选。

建议方向：

- 加作品详情/编辑页。
- 支持编辑场景列表、台词、选项、结局、封面、分身、IP、原创/二创声明。
- AI 作为辅助：续写、改语气、补分支、生成短标题、生成封面提示。
- MVP 先做结构化场景编辑器，不做自由代码编辑器。
- MVP 开放图片/音频上传，但必须有素材来源、内容安全和版权风险记录。
- 发布后修改可以选择暂存修改或发布更新；发布更新生成新版本，不直接覆盖历史版本。

已确认：

- 开放图片/音频上传。
- 发布后修改可以选择暂存修改或发布更新。
- H5 场景上限 MVP 先按 `30` 处理；硬件候选单独看复杂度。
- AI 标记按后台记录为主，商店/硬件或政策需要时再前台披露。

建议产出：

- `docs/creator-editor-plan.md`

## 08. 真实账号与后端缺失

优先级：`P0`

现状：

- 当前数据通过 mock API 和 `localStorage`。
- 没有真实登录、用户、权限、作品归属、订单、设备绑定。

风险：

- 无法进入真实测试。
- 审核、商店、收益、专区和设备权益都依赖账号体系。

建议方向：

- 保留当前 API facade，逐步替换成真实后端。
- 先定义核心实体：User、Work、Draft、StoreListing、HardwarePack、Device、Order、ReviewTask。
- `guguclub` 已废弃，Gugu Flash 是替代它的新主系统，不作为旧项目外挂。
- Gugu Flash 自建账号、用户、权限、设备、BLE/同步、支付、订单、下载和内容后端。
- Native / Web / 小程序共用同一套 Gugu Flash API。
- 旧 `guguclub` 只作为迁移参考：设备协议、BLE 经验、历史设备型号、内容包格式、可迁移脚本。
- 购买权益按设备落库，核心对象是 `DeviceEntitlement = deviceId + hardwarePackId`。

已确认：

- `guguclub` 已废弃，Gugu Flash 是替代它的全新项目。
- Gugu Flash 自建账号体系，不复用 `guguclub` 登录。
- Gugu Flash 自建设备、BLE/同步、支付、订单和下载能力。
- Native / Web / 小程序共用同一套 Gugu Flash API。
- 购买权益落到设备，不落到账号全局。

建议产出：

- `docs/backend-entity-api-plan.md`

## 09. 内容安全与社区治理缺失

优先级：`P0`

现状：

- 有评论计数，但没有真实评论、举报、拉黑、隐私、未成年保护。
- 没有敏感词、内容分类、年龄分级、私信安全。

风险：

- 角色扮演、二创、陌生人社交很容易出现擦边、网暴、骚扰和饭圈冲突。
- 未成年人场景下尤其高风险。

建议方向：

- 最早期就定义社区规则和举报处理。
- 评论、上传素材、私信、专区申请/邀请都要有风控入口。
- 对真人名人、恋爱 CP、未成年人、付费关系道具保持保守。
- MVP 不开放陌生人私信。
- MVP 不做 CP / 情侣 / 绑定关系玩法。
- MVP 不做付费关系道具。
- 评论可以开放，但必须有举报、拉黑、隐藏、删除、限流和审核记录。
- 未成年人默认强保护，未知年龄按保守策略处理。

建议先确认：

- 是否确认 MVP 不开放陌生人私信？
- 是否确认 MVP 不做 CP / 情侣 / 绑定关系玩法？
- 是否确认 MVP 不做付费关系道具？
- 是否确认评论开放但必须带举报、拉黑、隐藏、删除、限流和审核记录？
- 是否确认未知年龄按保守策略处理，未成年人默认强保护？

建议产出：

- `docs/safety-governance-plan.md`

## 10. 状态机容易漂移

优先级：`P1`

现状：

- 当前存在 `status`、`hardwareStatus`、`storeStatus` 三套状态。
- 这些状态在原型里可以工作，但真实系统中容易组合出矛盾状态。

风险：

- 例如作品已上架但被下架、硬件可下载但商店未上架、H5 被封禁但硬件包仍可购买。
- 状态判断分散在前端和 mock API 中，后端落地时容易重复造规则。

建议方向：

- 明确主实体和派生状态。
- 用状态表列出允许迁移和禁止迁移。
- 审核、商店、硬件适配使用不同实体，而不是把所有状态塞在 Work 上。
- 前端展示用的综合状态从多个实体派生，不反向写回主实体。

已确认：

- `Work.status` 只表示 H5 社区状态。
- `StoreListing.status` 和 `HardwarePack.status` 独立。
- `StoreListing` 代表商店申请/商品，`HardwarePack` 代表后台制作出的设备包。
- `Order`、`DeviceEntitlement`、`DeviceInstall` 独立。
- 购买权益按设备，不按账号。
- `HardwarePack` 下架后，已安装设备内内容可以继续使用。
- 下架后停止新购买、新下载和同步到新设备。
- 已上架或硬件化的 `WorkVersion` 不能直接覆盖。

建议产出：

- `docs/state-machine-plan.md`

## 11. 推荐、排序与数据指标还很粗

优先级：`P2`

现状：

- `scorePack` 根据点赞、收藏、Remix、播放、完播率和举报计算热度。
- Feed 频道按钮只是展示，没有真实过滤。

风险：

- 内容分发不可控。
- 新作品冷启动、专区推荐、好友推荐、商店转化都无法验证。

建议方向：

- 分 Feed：推荐、关注、IP/专区、题材、好友、商店候选。
- 指标拆清楚：播放、完播、选择分支、收藏、分享、评论、Remix、申请上架、购买、同步。
- 排序先规则化，不急着个性化算法。
- 长期北极星看每周设备端有效体验数。
- MVP 先导指标看有效播放数和合格发布作品数。
- 二创可以参与全局热门，但必须通过 IP、审核、安全、举报和多样性规则。

已确认：

- 长期北极星是每周设备端有效体验数。
- MVP 先看有效播放数和合格发布作品数。
- 推荐先规则化，不急着个性化。
- Feed 拆成推荐、关注、IP/专区、题材、好友、商店候选。
- 二创内容可以参与全局热门，但必须通过 IP、审核、安全和举报阈值。
- 专区开通热度由作品数、创作者数、有效播放、收藏、Remix、举报率综合计算。

建议产出：

- `docs/recommendation-metrics-plan.md`

## 12. 商业化与收益分配未定义

优先级：`P1`

现状：

- 商店里有价格、购买、下载、同步的模拟状态。
- 没有真实订单、退款、分成、结算、税务、收益冻结。

风险：

- 一旦允许用户作品上架，就必须处理收益归属。
- 二创内容商业化风险更高。
- 共创当前暂停，不进入 MVP 收益分配。

建议方向：

- 早期可以只做官方免费/低价内容包。
- 用户作品上架先不开放收益，或只做积分/荣誉。
- 等审核和版权机制稳定后，再开放创作者分成。
- 免费领取也要生成 `Order` 和 `DeviceEntitlement`。
- 用户作品上架先做荣誉、积分、徽章、署名和曝光。

已确认：

- MVP 不给用户作品立刻开放现金收费和现金分成。
- MVP 可以做官方免费/低价 `HardwarePack`。
- 原创和二创都可以申请上架，但二创商业化审核更严格。
- 二创默认不开放现金收益，除非有明确授权或平台活动规则。
- 共创当前暂停，不进入 MVP 收益分配。
- 购买权益继续按设备，不按账号。
- 收益冻结、退款、结算、税务模型先预留，现金分成后置。

建议产出：

- `docs/monetization-plan.md`

## 13. 设备同步链路仍是原型

优先级：`P1`

现状：

- 当前可以模拟绑定设备、下载内容、同步到设备。
- 没有真实 BLE、设备能力检测、下载失败、版本兼容、回滚。

风险：

- 硬件体验一旦失败，用户信任损耗很大。
- 不同设备型号、固件版本、屏幕尺寸会影响内容表现。

建议方向：

- 硬件包需要 `minFirmwareVersion`、设备型号、资源预算、校验和、安装状态。
- 同步流程需要失败恢复、重试、回滚、当前运行内容确认。
- Gugu Flash 自建设备绑定、BLE/同步、下载、安装状态和设备能力检测。
- 旧 `guguclub` 的设备协议和 BLE 经验只作为迁移参考。
- 已安装到设备内的 `HardwarePack` 允许离线使用。
- 新购买、新下载、新同步必须在线校验设备权益、包状态和设备兼容性。

已确认：

- 旧设备绑定不静默迁移；如需迁移，必须用户重新验证设备。
- 已安装到设备内的 `HardwarePack` 允许离线使用。
- 同步失败必须提供明确原因、重试入口、回滚策略和客服诊断码。
- `HardwarePack` 下架后，已安装设备内内容继续使用。
- 下架后停止新购买、新下载和新设备同步。
- Native App 是主同步客户端；Web/H5 只做展示和跳转。

建议产出：

- `docs/device-sync-plan.md`

## 14. H5 与硬件内容格式版本治理不足

优先级：`P1`

现状：

- `GuguH5Pack` 已经有结构化字段。
- 文档提到硬件 `story.json` 更受限，但转换规则还没落细。

风险：

- H5 越做越丰富后，硬件无法承接。
- 没有版本治理会导致老作品不能播放或不能转换。

建议方向：

- 给 `GuguH5Pack` 增加 schema version。
- 定义 H5 能力集和硬件可转换能力集。
- 硬件适配前输出兼容性报告。
- H5 发布和硬件上架拆开，H5 可以使用硬件暂不支持的能力。
- 后台适配后生成独立 `HardwarePack.id`，不改写原始 H5 版本。

已确认：

- H5 允许使用硬件无法支持的能力，硬件能力只影响上架和下载。
- 转换失败不影响 H5 发布，只会让硬件适配进入“需降级 / 需人工适配 / 不兼容”。
- 降级适配可以做，但必须由后台记录降级动作，不能静默改变核心内容。
- 官方适配后生成新的独立 `HardwarePack.id` 和 `HardwarePack.version`。
- `HardwarePack` 必须引用固定的 `sourceWorkVersionId` 和 `compatibilityReportId`。

建议产出：

- `docs/content-schema-versioning-plan.md`

## 15. UI/UX 仍偏原型

优先级：`P2`

现状：

- 当前 Web 原型能验证流程。
- 部分按钮、官方台、商店、个人页仍是演示风格。

风险：

- 真实用户会不理解“发布”“上架”“硬件候选”“可下载”的区别。
- 角色分身、专区、二创 IP、商店审核会让新手感到流程偏重。

建议方向：

- 把创建流程做成渐进式，不在第一屏堆太多概念。
- 对发布、上架、硬件适配做清晰状态提示。
- 商店和硬件页要明确当前内容能不能运行在设备上。
- 创作时先选原创 / 二创和 IP，再选择该 IP 内角色分身，不把专区当成必选项。
- 前台用“已发布、上架审核中、制作设备包中、可下载到设备”等用户语言，不直接展示“硬件候选”。

已确认：

- 创作入口默认原创，二创作为清晰可见的第二选项，不藏成复杂高级功能。
- 二创必须选择 IP 池里的 IP；找不到 IP 时引导申请添加 IP。
- 分身是 IP 内角色，角色列表应跟随所选 IP。
- 创作时不直接选择专区；有 IP 不等于有专区，专区是达标后申请开通的社区空间。
- 需要新手引导，但采用空状态、流程卡、上下文提示，不做阻塞式长教程。
- 移动端 App 优先，Web 分享页作为作品传播和跳转辅助。

建议产出：

- `docs/ux-flow-plan.md`

## 16. 测试与质量保障缺失

优先级：`P1`

现状：

- 当前有内容 schema 检查。
- 没有单元测试、流程测试、浏览器回归测试、状态机测试。

风险：

- 后续状态和流程增多后，很容易改坏发布、审核、商店、同步链路。
- 版权/审核规则如果没有测试，会出现越权或漏审。

建议方向：

- 给核心状态机和 API facade 加单元测试。
- 给关键浏览器流程加 Playwright 测试：原创发布、二创 IP 拦截、申请上架、批准上架、商店同步。
- 给 seed data 和 schema 增加更严格校验。
- 先保护版权、IP、商店、硬件包、设备权益、下架保留使用权等高风险规则。
- 原型阶段不做大面积视觉快照，把测试成本集中在业务规则和关键路径。

已确认：

- 单元测试和契约测试先用 Node.js 自带 `node:test`，避免一开始引入重依赖。
- 浏览器关键路径用 Playwright。
- CI 初期必跑内容校验、核心单元测试、状态机测试和 API facade 测试。
- Playwright P0 流程先作为 release 前必跑，稳定后纳入 PR 必跑。
- 原型阶段接受低到中等测试成本，但版权、上架、设备权益和下架规则必须自动化。

建议产出：

- `docs/testing-plan.md`
